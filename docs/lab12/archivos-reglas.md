# Archivos durables y reglas de admisión LAB12

Implementación en `archivo/{boi,bo,dao,impl}` y `ArchivoDigitalRS`. Los bytes se conservan en `archivo_digital.contenido` (MEDIUMBLOB MySQL); un SHA-256 permite comparar la descarga con el original. El backend valida propietario, extensión, MIME, firma, contenido, límite de 5 MB y fecha de registro según America/Lima. DNI/fotografía admiten JPG/PNG; certificados PDF. El tamaño/formato específico de cada requisito se verifica también en su procedimiento almacenado.

`ZonaCarga` conserva el callback de nombre y añade `OnContenido` con los bytes reales. RF05/08/11 usan `AdmitURestClient.Archivos.cs`, nunca MySQL desde C#. Los archivos se pueden visualizar y descargar con autorización. Evaluadores pueden consultar los bytes de documentos y vouchers mediante el visor del expediente; los registros históricos que únicamente tenían una ruta ficticia indican que no hay bytes asociados.

El certificado y su archivo se guardan en una transacción. El formulario permite indicar COLEGIO o UNIVERSIDAD; una institución nueva conserva el tipo seleccionado y no se reclasifica silenciosamente una institución ya compartida por otros certificados. El contrato JDBC anterior de siete parámetros se mantiene como wrapper compatible, mientras el DAO actual invoca GUARDAR_CERTIFICADO_METADATA_TIPADA con el tipo explícito. El voucher actualiza el pago generado existente, permite corregir/retirar un pendiente y bloquea aprobados. Un reenvío reemplaza el mismo archivo/pago, no crea pagos adicionales. El retiro y la aprobación concurrentes releen el estado bajo bloqueo de fila para que un aprobado no pierda su archivo. Los documentos aprobados quedan protegidos contra retiro; un documento sin archivo activo no puede aprobarse.

`PostulacionRS/enviarPostulacion` recibe `{postulacion,sedeId,documentos:[{requisitoAplicableId,nombre,mime,contenidoBase64}]}`. `PostulacionBOImpl.enviar` registra postulación, archivos, metadatos de documentos, pago generado e historial con la conexión ThreadLocal de `TransactionContext`; confirma solo después de validar todos los requisitos obligatorios y la sede. Un fallo revierte toda la operación. El servidor deriva el importe de convocatoria/modalidad y fuerza el estado inicial; no acepta un estado final del cliente.

La base impone `UNIQUE(postulante_id,convocatoria_id)` y un índice único sobre el pago vigente generado/pendiente/aprobado. La migración se detiene si encuentra duplicados previos, sin borrarlos. Se preservan sede/evaluador y se valida la convocatoria publicada, fechas, oferta y modalidad.

Las transiciones registran historial en SQL. La aprobación del pago avanza el expediente a revisión. Para APTA se exigen pago aprobado y documentos obligatorios aprobados con archivo activo. El carné solo se emite para aptos y completa la inscripción en la misma transacción. La anulación conserva la fila y utiliza el marcador `AulaExamen=ANULADO` ya interpretado por Blazor. No se puede trasladar un carné a otra postulación. Una subsanación guarda nueva versión y marca observaciones subsanadas; al resolver la última, un expediente observado con pago aprobado vuelve a revisión.
